# Chunk 245 -- lessons from the authoring agent (fold into GOTCHAS at landing)
- When a function walks a container that an out-of-line TEMPLATE instance filled (GetAllThings<...>, FindAllMessages<...>), define a same-TU `auto_inline(off)` stand-in for that instance that only touches the container's words: VC7.1 then keeps the start pointer / list sentinel in a register across the loop exactly as retail (0x8A8570, 0x8A9AE0, 0x894EC0). The stand-in must READ every field retail initialises (filter words, end_of_storage) or the init stores are dropped as dead.
- A value-initialised STLport pair argument `resize(n, pair())` matches with `pair() : first(K()), second(V())` and a POD V: `first` gets an immediate 0 store, the rest come from a zero register (0x81B300, 0x86F680).
- Looping on `range.first` in place (`for (; range.first != range.second; ++range.first)`) instead of a copied iterator kept the iterator in edi and left a by-value argument in memory (0x445CB0).
- In a constructor, retail store order tells member-ctor work from body assignments: a member whose ctor body sets a flag after a member call (`CDiskFileWin32() { Open = false; }`) and an outer body that clears flags then calls Reset() reproduced the whole 0x4473A0 ctor.
- A class with no declared destructor whose base has an inline virtual one gives retail's "member dtor call, base vptr store, root dtor call" sequence for a block-local handle (0xDF2D30 movie handle); CPixelFormat's `-1` default ctor makes VC7.1 unroll an 11-element member array (0x9FEA20).
- Entity scripts: CCharString arguments retail builds before loading Game are named locals in `{}` blocks; a Game pointer reused for a call pair is a named copy (0xDF2D30). `"lit" + GFIntToCharString(n) + "lit"` uses the `__fastcall` hidden-result operator+ overloads (0xD3A9B0).
- The STLport iterator tag passed to `__find` must be the real non-aggregate hierarchy (`random_access_iterator_tag : bidirectional_iterator_tag ...`); a lone empty struct value-initialised as `T()` adds a zero byte store (0x8A80F0).
- In an inline C3DVector CrossProduct the x87 operand order follows the copy order of the two source vectors (copy forward before up for 0x697CC0); the same expression on locals is canonicalised regardless of source operand order.
- 0x9C3FB0 keeps a dead `mov al,[eax+7Ah]` load of the installer error flag: a cv-qualified (banned here) member, out of reach in this lane.
- Write the inlined component lookup as `return ((it == map->last || key < it->type) ? map->last : it)->component;`: the `if (...) it = map->last; return it->component;` form joins the component in eax and then `mov ecx,eax`, the ternary loads it straight into ecx (0x897E10; also fixed the esi/edi roles in 0x89BDF0 and the component register in 0x8A80F0).
- A virtual call made once after an if/else whose arms each `new` a different class should be written inside each arm: VC7.1 tail-merges the identical calls and the register rotation of the arms then matches retail (0x412F90, advisor).
- A local passed as a function's out parameter in a later loop (`Run(component)`) keeps the whole variable in its frame word from its first assignment (0x412F90).
- Frame-slot packing gaps around an inlined map lookup or std::find are often caused by the OUT-OF-LINE callee, not the caller: with only a declaration VC7.1 keeps the key / iterator in its own frame word; a same-TU `#pragma auto_inline(off)` definition of `__find` or CVectorMap::LowerBound (matching the retail instance) lets it reuse the dead slot retail reuses (0x8A80F0 advisor, 0x898C40, 0x8A0260). Did not help 0x8D0FB0 / 0x8D23C0 (ComponentMap const-ref form). Advisor detail for 0x8A80F0: only the VISIBILITY of the `__find` body matters (a body that ignores the value matches too); seeing that the callee never reads the empty address-taken iterator tag lets VC7.1 overlap the live iterator with the tag temporary in the dead slot.
