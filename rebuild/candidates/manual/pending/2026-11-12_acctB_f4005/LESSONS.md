# Chunk 4005 -- lessons from the authoring agent (fold into GOTCHAS at landing)
- 0x00F2A250 CScriptDef::operator= (11.7 KB) is the IMPLICIT operator=: no statement of it is source. A long member-wise assignment whose every member is copied in declaration order by its type's own assignment (dword moves for long / float / CDefString, out-of-line calls for CCharString and STLport vectors) needs only the header without the declared operator= and a user (`inline` Copy + a vtable user). Check first with a member map (tools/map2.py: copy events v header members).
- c2 has a THIRD inline gate besides the cost rule and the budget rule (chunk 4004): a callee that is not yet compiled and passes the budget rule (c2.dll 0x107284A3) is expanded only if its IL statement count is at most (N + 2) * 3 + 3, N = arguments of the call (c2.dll 0x1078DA87 -> 0x107285BB -> 0x107284D5; opcode 0x0D counts 1, 0x0F / 0x13 count 2; K = [0x108A912C] = 3). For a thiscall operator= that is 15: ??4CDefClassBase counts 38, ??4CParentDefClassBase 51, ??4CVectorMap 7, ??4CArray / ??4CDefPointeeBase 4. A "budget accepted but still called" site is this cap, not a source difference. Hook: tools/inl/inl5.py (events `cnt`), inl6.py + C2_LIMIT for the full count.
- Consequence for def classes: the FIRST implicit operator= of a translation unit that reaches CParentDefClassBase::operator= calls it (retail 0x00F29F70 CRegionScriptDef: `call 0x00431ED0`); every later one in the unit expands it and CDefClassBase::operator= by the cost rule (sz=49 c1=44, sz=77 c1=72: retail 0x00F2A000 CCutsceneDef, 0x00F2A250 CScriptDef). "Expanded here, called there" between sibling def classes is their ORDER in the unit, not a forced inline. Review at landing: the FABLE_RETAIL_PDCB_FORCEINLINE_ASSIGN rows (0x004321F0, 0x00F2A000, 0x00432C70, 0x00432E60, 0x00434450, 0x004345A0) and the comment in engine/CParentDefClassBase.h ("no implicit / inline / out-of-line form gives both"): the implicit form does once an earlier user of the unit stands in front.
- 0x00431ED0 CParentDefClassBase::operator= (49 bytes, calls 0x00431F10, expands the CVectorMap copy) and 0x00431F10 CDefClassBase::operator= (77 bytes) are what VC7.1 writes for the implicit assignments when the parent one is compiled FIRST (inline-virtual / first-use order); compiled bottom-up (non-inline Copy) the parent swallows CDefClassBase's (105 bytes) and is then too dear to expand (c1=100).
- An inline virtual reached only through the vtable is emitted user first, then what it uses (Copy 0x00F2A240, then ??4CScriptDef 0x00F2A250, then the vector operator= instances from 0x00F2D010); retail's Copy-before-operator= layout for CRegionScriptDef / CCutsceneDef / CScriptDef says the def classes' Copy is inline. A non-inline Copy gets the implicit assignments in front of it.
- Cost-rule expansions also pay the budget: after ??4PDCB (57) and ??4CDefClassBase (108) the row's budget is 19358 - 165 at the CVectorMap site.
- The object order of two classes' vtable-driven groups depends on whether the base constructors are inline: with FABLE_RETAIL_DEF_CLASS_BASE_CTORS + FABLE_RETAIL_CVECTORMAP_CTOR (retail's inline base constructors) it is source order and the constructors equal retail's 0x00F28F90 / 0x00F29C10; without them the two groups came out reversed. Use retail's constructor shape before fitting the order.
- Free check that a row's unit models retail: grade the OTHER functions the unit emits against their retail addresses (tools/sib.py). Here all ten equal retail (0x00F29F60, 0x00F29F70, 0x00F29FA0, 0x00F29C10, 0x00431ED0, 0x00431F10, 0x00F2A240, 0x00F28F90, 0x00F29530, 0x00F29510).
- A copy test cannot tell a long member from a float one (both dword moves); pair an operator= row's test with the class's Transfer test for the member types.
