# agentP6 (w22) lessons, GOTCHAS-ready, one line each

- Water rows 0x00B6FA40 / 0x00B70230: the last `test esi,eax / or eax,esi` operand-order residue in the SetRenderState bookmark blocks is a c2 record-id tie set by the function's total IL record count (dead-sum ruler windows: mid N=2..9, bg N=4..16, location-independent); the FableWin donor's two release ASSERTs in the inlined SetSea*TexturesAndUVModes helper (FABLE_RETAIL_ASSERT(SeaBumpMap), FABLE_RETAIL_ASSERT(EnvironmentMap) with FABLE_RETAIL_ASSERT_DEAD_ARM) land in both windows -> RELOCATION_MATCH.
- A Codex pass-22 row that SRC_FAILs under the repo headers is usually missing its private header profile: materialize it from the pass zip (`tools/materialize.py`) and merge with `diff3 -m -E` (plain `-m` = -A gives spurious conflicts) onto the closest base (overlay45 or reference); a profile older than overlay45 merged on an overlay45 base deletes accepted text.
- equiv_check.py: EH funclet rows `#include "../src/compiled/..."` relative to the include dir, so a candidate tree outside rebuild/ gives 1,318 false cpp-error-new DIFFs; put the tree at X/include with X/src -> rebuild/src. Rows with an `if (0)` assert arm also differ by `__FILE__` (path only).
- 0x00BF0B20: the CRGBColour copy is scheduled as ld/st pairs in Initialise store order (R,G,B,A); retail's `mov cl,[ebp+0x14]` before `mov [esp+0x1d],al` needs the B pair indexed before the G pair, but every store order that does that also colours B first (B takes eax): node order and colouring order both follow the store order, so copy-ctor/Initialise bodies cannot reach it.
- 0x00F3E120: the reload order of `this` / vertex_to_poly_map at 0x00F3E291 and 0x00F3E3C5 follows split-piece numbers, which follow the first IL definition (not the declaration: declare-uninitialised then assign keeps the bad order); `best_start_vert` defined before `vertex_count` fixes both but then the prologue stores come out b,s,c (retail c,s,b, scheduler ties by IL index). A dead-sum ruler (N=1..24) does not move it.
- 0x0064BFBA: c1 canonicalises the operand order of `Bank.GetGraphicMaxHeight(..) * GPDisplayManager->GetRenderTargetDimensions().Y` (swap/cast/paren identical), and the width line (`.X`, offset 0) comes out dims-first while the height (`.Y`, offset 4) comes out max-first; binding the dims to a `const C2DExtentsI&` gives retail's dims-first order but extends the temporary into its own slot (frame 0xec v 0xe4) instead of retail's spilled return pointer [ebp+0x70].
- 0x00F3E120 (c2prio, 2026-11-15): integer root candidates 1 and 2 reuse the records of the two immediate-only constants (0x2aaaaaab, -1); `this` always gets const -1's record, so `this` precedes `vertex_link_map` in split order (and gets the later piece number that puts the map reload first) only when the -1 initialiser is walked before the size division -- which also moves best_start_vert's store ahead of vertex_count's. Dead first stores do not count (removed before the walk).
- 0x00BF0B20: the debug copy ctor 0x018BC5B0 pushes A,B,G,R into Initialise 0x018A0C60, which stores R first -- the PASS22 CRGBColour bodies are right; the residue is a scheduler tie (both 0x17400, sim.py formula), not a body choice. The donor's release-dead alpha_ref/alpha_bias locals and the copy/upload spellings are inert.
- 0x0064BFBA: VC7.1 orders `vcall(x) * Call().Y` max-first but `vcall(x) * Call().X` dims-first whatever the statement order or operand spelling; a const-reference binding forces dims-first but extends the temporary.
- 0x00675E20: Codex's 6 explicit CPersistContext::Transfer<T> specialisations are what make the bodies inline; the generic member template (FABLE_RETAIL_CPERSISTCONTEXT_TRANSFER_BINARY_BODY) is not inlined there at all (685 v 1912 bytes, /d2inlT512 too).
- Merging an old Codex profile: choose the diff3 base per file by fewest deleted repo lines (then conflicts); the "closest base" rule turned other rows' opt-in text into deletions (tools/mkovl2.py).
- c2 constant records (0x00F3E120, hooks at 0x1077FF77 / 0x10784DA6): after the constant candidates are built, c2 frees every constant with use count 0 in hash order (64 buckets, value & 0x3F, newest first within a bucket); the next root candidates (this, then the parameters) pop those records LIFO and keep their ids, so the immediate-only constants' VALUES decide the first root ids and through them later split-piece numbers and reload order.
- 0x00BF0B20 (agentP6F): an assignment to a float local (`width *= 1.0f/mesh_scale;`) leaves a no-op tuple (op 0x269) in c2's block DAG after the fmul; it adds 1 to the height of everything upstream. Here the G store 0x00BF0B39 waits on the glow load (eax anti-dependency), whose height runs down the fmul chain, and one extra 0x269 made its priority tie the B load 0x00BF0B36 (0x17400 each, lower index = the store first). Folding the reciprocal into the upload arguments (`width*(1.0f/mesh_scale)*0.01f`) removes one 0x269 per chain: store 0x16c00 < load 0x17400 -> RELOCATION_MATCH. When a scheduler tie is the residue, count the 0x269 nodes on the tied node's dependency chain before touching the tied statements.
- c2 constant candidates (0x00F3E120, hooks tools/sched/tw.py, tu.py, tnew.py): the syms are made by one walk over the lowered tuples (0x1077D560 -> 0x1077E132) in tuple order; a constant with one use outside any loop is put back as an immediate (use count 0) and its record is freed for the first root candidates, two uses or one use in a loop keep it. `long best_start_vert = 5;` instead of -1 (bucket 5 instead of 63) fixes both reloads of 0x00F3E120 and differs only in the immediate, so that free order is the whole residue.
- c2 operand order for `call(args) * call().member` (0x0064BFBA, micro/o1..o13): an operand that is exactly `*(call)` (member at offset 0, reference- or pointer-returning call) has its call made first and the pointer kept across the other call; `*(call + N)` does not, unless the other call has no variable argument. Inline helpers around the temporary give dims-first but move the CSE'd receiver load after the call.
- c2 scratch rotation (0x00675E20): besides the per-function reset, the rotating pointer is reset only at pseudo-tuple 0x2d3, which exists only under c2 -ZI (edit and continue; refused with /O2, and /Zi /d2ZI stops inlining) -- not a retail lever. Retail's eax,eax,eax temps are non-rotation assignments (the stream argument of the inlined class-type traits arms and the CCountedPointer::operator* result); debug flags /Zi /Z7 /Zd and EH flags do not reproduce them.
- Wine lane: the first cl.exe run after a fresh container starts wineserver's services, which inherit q.py's capture pipe; that first grade never returns. Stop it and rerun (later runs take 1-20 s).
- 0x00675E20 (agentP6F, matched): an `__assume` anywhere in a function (here the TransferVector NODEFAULT `default: { __assume(0); }`, FABLE_RETAIL_CPERSISTCONTEXT_TRANSFERVECTOR_NODEFAULT) stops VC7.1 forwarding the arguments and return values of inlined callees; they stay variables, the global allocator gives them eax and they do NOT advance the eax/ecx/edx scratch rotation. Signature in retail: several consecutive short-lived temps all in eax (0x00675E43, E50, E5B, E80, E8D) and the rotation starting one step late (0x00675EA7 eax, 0x00675F7A ecx). For a parked "scratch rotation phase" row, first check whether an inlined callee's switch in retail lacks the default test (`sub eax,2 ; je` without `dec eax ; jne`) and enable the matching NODEFAULT opt-in.
- c2 inline return values (micro/t1.cpp): a two-return or `?:` inline body (`if (Data) return *Data; return *Data;`) also leaves the result an allocator candidate (a c a d a), an empty Validate()/Fail() call or an `if (0)` dead arm does not.
- 0x0064BFBA: retail's order (receiver load, dims call, argument push, vcall, `imul eax,[p+4]`) is reproduced in a micro TU only by `*(call)` at offset 0, by a left call without variable stack arguments, or by an inline accessor for the receiver together with an inline reference pass-through of the temporary; __assume does not change the order.
