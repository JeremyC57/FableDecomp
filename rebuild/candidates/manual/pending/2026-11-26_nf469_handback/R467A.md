# R467A: is retail's ~CAIStateGroupBase implicit or user-declared? (NF469, 2026-11-26)

## Decision: IMPLICIT (compiler-generated)
One form for the whole base class: the destructor stays implicit in every view and port, and 0x008FD288 must become a
pick-any (thin) row with its grade and Leaf unchanged. The reshape is blocked first by 11 landed objects whose own pick-any
copy is not retail's (see "Blocker"), so the batch order is bR0 (11 rows, copy removed), then bR1 (0x008FD288 thin), then b1/b2.

## Evidence for (a), four independent sources
1. **PDB type records, both PDBs, with controls** (`llvm-pdbutil dump -types`, evidence/r467a/pdb_dtor_attrs.txt):
   - Ego_r: `~CAIStateGroupBase` attrs = `public virtual compiler-generated` (field list 0x3872C; also `operator=`,
     `__local_vftable_ctor_closure`, `__vecDelDtor` compiler-generated). `~CAIStateGroup_StandStill` is also compiler-generated.
   - FableWin: the same (`public virtual compiler-generated`, type 0x3C7C6).
   - Controls with user-declared destructors carry no such flag in either PDB: `~CBaseClass` (`public intro virtual`),
     `~CCharString` (`public`).
   - The shared header already says so: engine/CAIStateGroupBase.h line 11 "both PDBs declare no ~CAIStateGroupBase (the implicit destructor)".
2. **VC7.1 bytes decide here (the brief's "an explicit empty dtor compiles the same" is false for this class)** (exp/dtor/*.cpp):
   - implicit: `??1CAIStateGroupBase@@UAE@XZ` 19 bytes, no vptr store, COMDAT sel 2 (pick-any).
   - user-declared inline `virtual ~CAIStateGroupBase() {}`: 25 bytes, starts with `mov dword ptr [esi], ??_7CAIStateGroupBase@@6B@` (sel 2).
   - user-declared out of line: the same 25 bytes, sel 1.
   - The difference is the vptr store a user destructor of a non-novtable class emits. The landed 0x008FD288 only reaches 19 bytes
     by adding `__declspec(novtable)` to a local model.
3. **Retail bytes**: 0x008FD288 is 19 bytes, `push esi; mov esi,ecx; lea ecx,[esi+0Ch]; call 0x0099EAE0; mov ecx,esi; pop esi;
   jmp 0x0099A2E0`: no vptr store. The class is NOT novtable in retail: its ctor 0x008FD255 stores vtable 0x01288C60
   (`mov dword ptr [esi],1288C60h` at 0x008FD260) and RTTI .?AVCAIStateGroupBase@@ exists. A user-declared dtor would store it.
4. **Retail placement = a COMDAT of one TU**:
   - Retail 0x008FD255 (base ctor, unaligned, no padding before it) is followed with no gaps by the base's inline virtual bodies
     0x008FD26F..0x008FD287 (slots 2..5, 7..11, 13), then ~CAIStateGroupBase 0x008FD288, then ??_GCAIStateGroupBase 0x008FD29B
     (which calls 0x008FD288). That is the COMDAT run of a size-mode TU that defines the base ctor.
   - FableWin.pdb puts the ctor, ~CAIStateGroupBase, ??_GCAIStateGroupBase and 214 CAIStateGroup_* ctors/dtors in one object,
     `debug\ai_brain_tables.obj` (fablewin_obj_functions.tsv; Ego_d carved functions agree for the base ctor/dtor). A user
     destructor would have its own out-of-line home in the class's .cpp object.
   - So one copy at 0x008FD288 with callers in many functions is the linker's kept COMDAT, not a strong out-of-line definition.

- **Who emits:** ctor rows on the shared retail view (implicit dtor; e.g. 0x008FE862 ApprenticeHero, 0x008FF720 EnemyCreatureBase,

- **Who only declares:** 640 local models carry `virtual ~CAIStateGroupBase();` (declaration only); all 142 rows that call

## Blocker found: 11 non-EQ pick-any copies at HEAD
Once 0x008FD288 is pick-any, the linker keeps the first copy in link order. 11 landed objects emit a copy that is not retail's:
0x009000BC, 0x009004E0, 0x00900B41, 0x0090143E, 0x00902FB9, 0x00903216, 0x009126C0, 0x00918230, 0x009182D0, 0x00919A40, 0x00927C00
(all CAIStateGroup_* ctor rows on local models; locks all released). Their copies must go before bR1 lands. Proposed (ruling r469a):
declaration-only, the established local-model form (`virtual ~CAIStateGroupBase();`, as 640 landed local models): the copy disappears,
the ctor and every other function keep their bytes and relocation symbols. The proper end state is the r459a port of each onto the
shared header (wave 2), which also gives an EQ copy.

## Reshape owner for 0x008FD288 (bR1)
- The natural owner, the base ctor 0x008FD255, cannot emit the copy alone: with one caller in the TU VC7.1 inlines the implicit dtor
  into ??_GCAIStateGroupBase (measured: HEAD 40-byte and ported 38-byte ??_G, no ??1 symbol; retail's 28-byte ??_G calls 0x008FD288).
  With a second caller (any derived ??_G) the size-mode TU keeps ??1 out of line and the base ??_G becomes retail's 28 bytes
  (exp/dtor/implicit.cpp). Retail's ai_brain_tables TU had 214 such callers.
- So bR1 makes 0x008FD288 a thin row of a derived ctor unit of the same retail TU (ai_brain_tables) whose HEAD object already emits
  the EQ copy (ruling r469b on the owner choice).
