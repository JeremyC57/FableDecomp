## FableForge container-writer audit — 6 further defects (2026-08-21)

Summary re-homed to docs/modding/README.md#findings-that-live-in-fableforge on 2026-09-07; full text kept here (FableForge-owned).

Multi-agent audit of every container writer against zero-exception retail
invariants, each finding independently re-measured by a separate verifier.
Full report: `work/terrain_runtime_probe_20260821/FORGE_WRITER_AUDIT.md`.

**Fixed this session (both measured, both verified against the donor as control):**

1. **Quad-directory AABBs kept donor world coordinates.** Retail: every live
   quad-dir AABB lies inside its own map's InfoBlock box — 10257/10257 live
   entries across 332 maps, zero exceptions. The bake relocated vertices and
   patches but never the directory AABBs, so a chunk baked to (3328,2304) still
   carried Darkwood_3's (3104,2560) box: 16/16 outside. Added
   `forge::stbbake::translateQuadDirXY` and call it after
   `updateQuadDirZBounds` (which by contract writes only minZ/maxZ).
   After: 16/17 inside the declared box, matching the donor's own 16/17.

2. **Repacked foreground frames packed byte-tight.** Retail: 10257/10257 live
   `frameOffset` values are multiples of 2048, zero exceptions, each frame
   padded to the next boundary. The repack loop advanced by the raw compressed
   length. Before: 15/16 misaligned. After: 0/16. The comment at
   `apps/forge/main.cpp` claiming "retail packs frames tightly, not
   page-aligned" is factually wrong and is now corrected in code.

**Still open (measured and verified, not yet fixed):**

3. `wad::repack` does not align resized payloads or the footer (same class as
   the fixed `appendClonedEntries`; live path — `install-level` calls it
   whenever `--lev/--tng` custom bytes differ in size from the donor).
4. Appended STB chunk lands physically before the relocated common header,
   breaking offset/index monotonicity (retail: 0 violations across 423 pairs).
5. New WLD region omits 7 layout keys retail writes 141/141 times
   (`MiniMapScale`, `MiniMap/WorldMap/NameGraphic` offsets); two of them have no
   parse branch or struct member at all.
6. A map ends up owned by TWO regions. Retail map->region containment is a
   strict partition (BWD owner histogram `{1: 398}`); ours is `{1: 398, 2: 1}`
   because `--also-contain-in-region` adds to `containsMaps` rather than
   `seesMaps`. This is the host-region attach we rely on, so it needs care.

Cosmetic (measured, no plausible fault path): STB common-header name index
appended at tail instead of sorted position (consumer builds a red-black map, so
insertion order is irrelevant); appended STB entry writes dev-header `type=0`
where retail is `{1: 424}`; appended STB entry name length includes a NUL where
retail stores lengths without one.

Caveat on `stbvalidate` S3: it flags frames "neither page-aligned nor run-on"
using a 4096 page. Only 5414 of retail's 10257 frames are 4096-aligned, so
retail itself would trip this warning — S3 is a heuristic, not an invariant.

# 2026-08-28 — StatueMaster cut-design and augmentation-category recovery

An exhaustive cross-build/data audit materially sharpens the StatueMaster
picture. TLC retail `Fable.exe`, PDB-backed `FableWin.exe`, and PDB-backed
`ego_r.exe` all initialize `SM_Guild` but contain no
`TEXT_QST_061_STATUE_GUILD` reference or Guild reward/presentation branch. The
retail and Xbox-lineage text headers retain that tag at ID 3497, and English
`text.big` decodes it as “The statue is pointing to the Guild.” The available
PC builds therefore removed a distinct Guild presentation state. The original
Xbox `default.xbe` is unavailable locally and remains a material cross-version
gap, especially because a 2004 player recalled seeing a Guild Hall direction.

Five further orphan localized tags survive: Fire, Steel, Silver, Diamond, and
Lightning Statue Master inscriptions. None is referenced by any of the three
PC executables, extracted TNG/GTG/QST/INI, compiled game/script catalog, or
plausible numeric-ID/CRC representation. No surviving hit-response entity is
bound to them. However, `game.bin` preserves exactly five matching augmentation
inventory categories: Flame, Extra Damage (localized Steel), Silver, Diamond,
and Lightning. Retail objects map Extra Damage/Steel to
`OBJECT_SHARPENING_AUGMENTATION` and Diamond to
`OBJECT_PIERCING_AUGMENTATION`. This exact mapping is high-confidence evidence
for an abandoned augmentation-keyed Statue Master design.

All extracted placements of the five retail augmentation objects are ordinary
chest contents. The strongest physical fossil is Greatwood: the scripted
StatueMaster chest contains Piercing and is flanked by two unique
`OBJECT_LOOKOUT_POINT_STATUE` objects with blank readable overrides and no
scripts. This supports, but does not prove, a former Diamond/Piercing strike
puzzle. The released generic statue text concerns disturbed plants.

The native Bowerstone cellar branch additionally requires the dynamically
spawned `QR_EscortTrader` creature named `TraderToEscort`. Exact TLC xrefs show
that StatueMaster is the only consumer outside the escort quest itself. The
submitted Lua port comments out the lookup and is therefore not behaviorally
identical. Full evidence: `docs/scripts/STATUEMASTER_LUA_PORT_AUDIT.md`; synthesized
report and explicitly speculative restoration design:
`docs/scripts/STATUEMASTER_DEEP_RESEARCH_REPORT.md`.

## 2026-10-13 — Family landing: open codegen questions

Shapes that resist VC7.1 under every lander sweep setting (pragmas "", s, t, g, off; /GS; /Oa; /G3..7; /GR-):

- **F15 (76 bodies, no-RTTI module 0x00CDD000..)** `push esi ; mov esi,ecx ; call Base::Base ; mov eax,[esp+0Ch] ; mov ecx,[esp+8] ; mov [esi+40h],eax ; mov [esi+44h],ecx ; mov [esi],vtable ; ... ret 8`. Init list, body assignment, inlined `Set()`, embedded pair member, inlined intermediate base, `long` members, table-pointer member and inline-defined ctor all place the vtable store between the two member stores. The inlined copy of the same ctor inside the `Alloc` factory (F16) matches, so the shape is real but its out-of-line emission is not understood.
- **F73 (14 bodies)** scalar deleting destructor: member destructor at +off, `test [esp+8],1`, intermediate-base vtable store, delete. `__declspec(novtable)` on the derived class (which solves the plain-destructor sibling F143) removes the store entirely here (31 bytes) or leaves both stores (45 bytes).
- **F148 (9 bodies)** `mov eax,[esp+4] ; mov ecx,[ecx+24h] ; push eax ; call Method ; ret 4`: every __thiscall forwarder VC7.1 builds becomes a sibling `jmp`; void/long/bool returns, __stdcall callee and `optimize("y",off)` do not reproduce the call.
- **F14 of the 128-byte scan (46 bodies)** `push ebp ; mov ebp,esp ; push 0 ; lea eax,[ebp+0Bh] ; push eax ; push [ebp+8] ; call _Copy_impl/_Copy_backward<T*,T*> ; pop ebp ; ret 8` is the retail Dinkumware `std::copy`/`copy_backward` front end passing `_Ptr_cat` + `_Range_checked_iterator_tag` to an out-of-line `_Copy_impl`. The DDK 3790.1830 `<algorithm>` used by the lane inlines `_Copy_impl` into `copy` (50 bytes), so the retail STL headers are a different Dinkumware revision from the DDK's; shapes that depend on the retail STL header internals (this one, `_Buynode` variants, `_Uninit_fill_n`) must be written out by hand rather than through `#include <algorithm>`.
- **EH module (0x00C09000..) F467/F624 (9 bodies)** keep `this` in edx across an out-of-line constructor call (`mov edx,ecx ; push eax ; lea ecx,[esp+4] ; call ctor ; lea ecx,[edx+4]`): a normal __thiscall callee may clobber edx, so this is a custom (link-time) calling convention — the module was probably built with /GL. The same shape with `this` in esi builds fine under /EHsc (81 vs 77 bytes). **F15 `CDefinitionManager::GetDef<T>` (46 bodies)** matches everywhere except the temporary's release, which retail does as `mov esi,[eax+4] ; mov ecx,eax ; add eax,4 ; dec esi ; mov edx,esi ; test edx,edx ; mov [eax],esi ; jne` (count decremented in a register, a copy tested, stored through a formed pointer); eight source forms (reference, pointer, inlined helper by reference/pointer, explicit temporaries) give `dec dword ptr [..]` or a direct register test instead.
- **256-byte scan F4 (163 bodies, script module `C*Script::Main`)** `Add(new CSpawnedFunc_X(CCharString("LIT", -1), 0, this), CCharString("NAME", -1))` reproduces everything (139 vs 136 bytes) except two details: retail keeps the first CCharString temporary in the LOWER frame slot and zeroes the upper slot at function entry, and re-derives the temporary's address (`lea eax,[esp+10h]`) for the constructor call instead of reusing eax. By-value `CCharString` parameters (trivially copyable: the class has no user copy constructor) push the dword, not the address, so that is not it either. Parked.
- **256-byte scan F32/F47/F53 (56 bodies)** — the default-optimisation `_Tree::insert` (no frame pointer, `iterator::operator--` called on the stack object) builds 183 bytes against 180: retail overlaps the `_Insert` hidden-result temporary with the `where` iterator in the dead value-reference argument slot, VC7.1 here allocates one extra local for it (`push ecx`). Assigning the result into `where`, a `void` decrement, declaring `where` before the loop and a single-return form do not change it. The frame-pointer sibling (h16, same source) matches.
- **256-byte scan F17/F23 (72 bodies, retail vector grow-and-insert `Insert(where, const T&, const Tag&, count, noTail)`)** — `size + max(size, count)` growth with a reference-returning `Max` (lea pointer-select), malloc/memmove/free, `(char*)memmove(..) + bytes` return-value form: 30+ source spellings (named/unnamed capacity, count copies, loop forms, allocation branch orders, address-taken buffer, struct-wrapped buffer, pragmas and flags) reproduce every instruction except the register assignment: retail keeps `count` in edi for its whole life and spills `buffer` into the dead `count` slot (`push ecx` frame), VC7.1 here reloads `count` from its home and gives edi to `buffer` (`sub esp,8`). An indexed fill loop (`out[n] = *value`) flips the assignment but changes the loop. Same class as the QFE-4035 regalloc coin-flips.
- **256-byte scan F33 (24 bodies, `CPersistTraits<T>::TransferIn` forwarders, `ret 0Ch`)** — `Helper(value, item-by-value, ctx); return value;` builds 31 vs 29: retail pushes the first argument from its slot and re-reads it after the call; VC7.1 here caches it in esi. Hidden-return-pointer forwarding, reference/pointer parameters, a destructor on the 4-byte item and separate temporaries do not change it.
- **256-byte scan F24 (31 bodies, non-frame-pointer `TransferBinaryIn`)** — same source as the landed F9 (70) builds the identical 129 instructions with the three duplicated `*out = value` tails, but the `jb`/`ja` range-check exits target the other two copies; the orderings of the two comparisons and the `!(a && b)` form do not move them.

A named result local, do/while, reverse-iterator objects and the pragma sweep do not reproduce the folding.

- **512-byte scan F105 (9 bodies, `CRetailVector_dword(const CRetailVector_dword&)`)** — null the pointers, malloc the source size, memmove-copy: every instruction reproduces (95 vs 95) with a register assignment difference only. **F66 (12, `Clone()` with two trailing dword members)** needs the family-29 clone template generalised to N members (59 vs 71).
